# Gymtastic: Smart Gym Management System - Agent Guidelines

## 🎯 Project Overview
**Gymtastic** is a lightweight, monolithic web application designed to automate gym operations. It features smart member authentication, cashless transactions, real-time congestion monitoring, and IoT-integrated smart lockers.

**Tech Stack:**
- **Framework:** FastHTML (Python)
- **UI:** MonsterUI + HTMX (Server-Side Rendering with dynamic updates)
- **Database:** SQLite (via SQLModel ORM)
- **Architecture:** Layered (Presentation, Application, Data)
- **Package Manager:** **`uv`** (Required for all dependency management and execution)

## 📁 Project Structure & Module Organization

This repository is currently a minimal Python application.

- `main.py`: current entry point; keep startup logic here or move it into a package as the app grows.
- `pyproject.toml`: project metadata and Python version requirement (`>=3.14`), managed by `uv`.
- `uv.lock`: Lock file generated by `uv`. **DO NOT EDIT MANUALLY.**
- `README.md`: reserved for user-facing project documentation.
- `AGENTS.md`: This file (Developer guidelines).
- `*_llms-ctx.txt`: reference material; treat these as support files, not executable source.
- `gymtastic.db`: SQLite database file (generated at runtime). **Must be in `.gitignore`.**

If the codebase expands, place application modules in a dedicated package directory such as `gymtastic/` and keep tests under `tests/`.

## 🛠️ Build, Test, and Development Commands

**All commands must use `uv` to ensure environment consistency.**

- `uv sync`: Install all dependencies defined in `pyproject.toml` and `uv.lock`.
- `uv run main.py`: run the current application locally (Default: `http://localhost:5001`).
- `uv run python -m py_compile main.py`: quick syntax check for the entry point.
- `uv run pytest`: run the test suite once tests are added.

> **Note:** This project does not currently define build scripts or tool-specific tasks in `pyproject.toml`, so keep local commands simple and explicit. **Do not use `pip` directly.**

## 💻 Coding Style & Naming Conventions

Use standard Python conventions:

- 4-space indentation; no tabs.
- `snake_case` for functions, variables, and module names.
- `PascalCase` for classes.
- Keep functions small and focused; prefer explicit imports.

Follow PEP 8 and add type hints for new code where practical. If formatting or linting tools are introduced later, document them in `pyproject.toml` and update this guide.

**Stack-Specific Conventions:**
- **Presentation:** Use `MonsterUI` components and `HTMX` attributes (`hx-get`, `hx-post`).
- **Application:** Keep business logic in route handlers or service functions.
- **Data:** Use `SQLModel` for all database interactions. No raw SQL unless necessary.

## 🧪 Testing Guidelines

There is no test suite yet. Add tests under `tests/` using `pytest`, with filenames like `test_main.py` and test names like `test_prints_greeting`.

For new behavior, include at least one automated test or document why testing is not yet feasible. Prioritize coverage for CLI behavior and any future business logic extracted from `main.py`.

## 📝 Commit & Pull Request Guidelines

This repository has no commit history yet, so adopt a clear convention from the start:

- Write commit subjects in the imperative mood, for example: `Add CLI entry point`.
- Keep commits focused on a single change.
- Reference issue IDs in the body when applicable.

Pull requests should include a short summary, testing notes, and screenshots only if UI output is introduced later.

## 🔒 Configuration Notes

Keep secrets out of the repository. If environment-specific settings are added, load them from environment variables and document required keys in `README.md`.

## 🤖 AI Agent Instructions

When assisting with this project:
1.  **Enforce UV:** Always generate commands using `uv run`, `uv add`, or `uv sync`. Never suggest `pip install`.
2.  **Respect the Stack:** Always suggest solutions using **FastHTML**, **MonsterUI**, and **SQLModel**. Do not suggest Django, Flask, or React unless explicitly requested.
3.  **Layered Architecture:** Ensure code respects the separation of Presentation (UI), Application (Logic), and Data (DB).
4.  **HTMX First:** Prefer server-side rendering with HTMX for dynamic updates over client-side JavaScript frameworks.
5.  **Minimalism:** Keep the codebase lean. Avoid over-engineering (e.g., do not add a Repository pattern unless absolutely necessary).
